# Business problem

Week of November 15. Security operations needs a way to prioritize suspicious authentication activity without reading every login by hand.

## Situation

A 36-person company, rostered across Chicago, New York, and Austin, signs in to the same identity service all day. Over 2–13 November 2026 the extract holds 1,124 attempts. 1,069 succeeded. 55 failed. An analyst who opens the log in time order spends almost all of that time on ordinary office traffic: a Windows laptop on the office network, MFA satisfied, between 8:00 and 16:59 Chicago time.

The failures are not evenly interesting either. Most are a single wrong password. A handful are a password tried against many accounts from one address, or many passwords tried against one account, or a success that follows that burst from a country the account has never used.

## Decision this analysis supports

Which attempts should a person read first, and which facts on the attempt justify that place in the queue?

The output is an ordered queue with a sentence per fired rule, plus a set of SQL cuts that find the same patterns before any Python score is applied. The score bands in `docs/risk-model.md` are the operating definition: medium and above is the queue. Low stays in the log.

## What success looks like

On this file the queue is 24 attempts out of 1,124 (2.1%): 12 medium, 10 high, 2 critical. Both critical rows are successes that followed hostile context, which is the order security operations cares about. A success is the moment a session exists.

The same run leaves 1,100 attempts at low. That includes the ordinary morning login, a single wrong password, a new phone at lunch in the United States, a late-night login from the usual laptop, and the second and third days of a Berlin trip once Germany is already in that user's history.

A weaker result would be a single score with no sentence, or an IP list that ranks the Chicago office address next to a spray because both have "many failures" when the office address also has 310 successes.

## Scope

In scope: describe the file, load it to PostgreSQL, count the patterns the columns can support, and score each attempt from those columns plus earlier attempts.

Out of scope: blocking an account, paging an on-call rotation, and any claim about how many account takeovers the queue contains. The extract has no takeover label. Authorization decisions are absent too, so the queue does not say what the session did after it opened.

## Data used

`data/raw/authentication_events.csv`, profiled in `docs/data-profile.md`. No production sign-in export was in the workspace. The file is a seeded teaching extract in the shape of an interactive sign-in log, regenerated by `src/generate_auth_events.py` with seed 21. Every IP address is in an RFC 5737 documentation range.

Counts below were checked two ways. `src/load_events.py` loaded 1,124 rows into `authentication_risk.auth_events` and matched the CSV on rows, users, successes, failures, and sessions. `pytest` scores the file and expects 1,100 low, 12 medium, 10 high, and 2 critical.
